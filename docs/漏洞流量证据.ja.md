# 脆弱性の複数トラフィック証拠

脆弱性詳細の「関連トラフィック」は、ページをまたいだ複数選択、用途と説明、並べ替え、およびバインド解除をサポートします。トラフィックページでも複数のレコードを選択し、一度に既存の脆弱性へ関連付けできます。タスクから継承した脆弱性証拠は読み取り専用で、変更するには発生元のタスクに入る必要があります。

システム設定の「Agent 自動トラフィックバインド」はデフォルトで無効で、読み取りと変更のインターフェースは `/api/settings` の `agent_traffic_binding` です。有効にすると、リクエスト/レスポンスの参照、ツール呼び出し、プロンプトによる Token 消費が増加します。次のラウンドの Agent から新しい設定が適用されます。無効時は自動バインドのパラメータと補完バインドツールを非表示にし、自動バインドの案内を注入せず、すでに実行中のセッションから新規に提出された自動バインドを拒否します。手動バインド、トラフィックキャプチャ、保存済み証拠の読み取りおよびエクスポートには影響しません。

有効化後のデフォルトのフローは「発見して登録 → 自動的にレポート Agent をトリガー → トラフィックを照合してバインド → 最新の証拠バージョンに基づきレポートを作成」です。報告者は `evidence` に検証コマンド、主要な出力、既存の実トラフィック ID および用途を残します。レポート Agent は脆弱性詳細と実行記録を踏まえ、`traffic_search` / `traffic_get` で確認したうえで `bind_finding_traffic` を呼び出し、その後最新の `version` を読み取ってレポートを保存します。スイッチを無効にしている場合、レポート Agent は追加で生のトラフィック検索/読み取りツールを得ることはなく、自動バインドも行いません。それでも手動でバインドされたスナップショットを読み取ってレポートを生成できます。

既存の呼び出し元との互換性を保ちます。`report_finding` の `traffic_refs` / `evidence_hint_id` は引き続き明示的な即時バインドが可能です。バインドは任意です。TCP などの非 HTTP 脆弱性、未採取または正確なレコードが見つからない場合は、参照を省略しても通常どおり報告およびレポート作成ができます。コマンド出力やログなど他の検証可能な証拠を残し、バインドしなかった理由を説明することを推奨します。必須フィールドは追加しません。提出された ID はすべて有効であり、本文が完全でなければなりません。いずれか 1 件でも失敗した場合は、今回のバインド操作をロールバックします。報告と同時の明示的なバインドが失敗した場合は、報告全体をロールバックします。同一スナップショットを重複して追加してもバインドは増えず、説明も上書きされません。

## Agent 番号とレポートバージョン

`report_finding` に任意のパラメータを追加しました。配列の順序がそのまま初期の証拠順になります。

```json
{
  "traffic_refs": [
    {"traffic_id": "真实流量ID", "role": "baseline", "note": "正常账户请求"},
    {"traffic_id": "另一个真实流量ID", "role": "proof", "note": "复现请求"}
  ]
}
```

用途は `baseline`（正常な対照）、`proof`（脆弱性の証明）、`verification`（補足検証）、`supporting`（補助証拠、デフォルト）です。まず `traffic_search` / `traffic_get` で実レコードを照合します。ドメインと時刻は候補の絞り込みにのみ使用し、タスクへの帰属を推定しません。

プロンプトは [CyberStrikeAI の脆弱性報告ツール案内](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go) を参照し、本プロジェクトの任意バインドの取り決めと組み合わせます。バインド欠落理由を必須とする検証は導入しません。ID を推測してはならず、バインドを補うためだけに探査を繰り返すべきではありません。

返り値の 1 行目は引き続き `finding recorded: <探索节点 ID>` です。続く JSON で独立した脆弱性レコード `finding_id`、探索ノード `finding_node_id`、およびバインドの概要を提供します。

- `get_finding_traffic(finding_id)` は**独立した脆弱性レコード ID**を使用し、順序付きリストと `version` を返します。`binding_id`、`side=request|response`、`offset`、`length` を渡すと分割読み取りが可能で、各セグメントは最大 8192 バイトです。
- `update_finding_report` の `finding_id` は**引き続き探索ノード ID を使用します**。実際に読み取ったバージョンを入れる `evidence_version` を追加しました。生成中に証拠が変化すると古いバージョンの書き込みを拒否し、再読み取りと再生成が必須になります。
- 旧レポートの呼び出しがバージョンを渡さない場合、既存のトラフィック証拠を上書きしたとは主張しません。バインド、説明、用途、または順序が変化すると、既存レポートに更新待ちと表示されます。

自動バインドを有効にすると、`add_hint` / `add_task_hint` は単一ヒント内、またはバッチ `hints` の各要素内で `traffic_refs` を保存できます。Planner が代理で報告する際は `evidence_hint_id` を渡し、本タスクに対応するヒント内の参照を明示的に選択できます。継承ヒントは参照できません。システムはドメイン、時刻、閲覧履歴からバインドを推測しません。提出が失敗した場合、部分的な脆弱性を生成したり、レポートを前倒しでトリガーしたりしません。

既存の脆弱性でバインドが漏れている場合は、`bind_finding_traffic(finding_id, traffic_refs)` で補完バインドでき、再登録は不要です。`list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail` は明確な `finding_id` と `finding_node_id` を返します。旧 `id` は探索ノードの意味を保持します。

起動時には旧ツールの schema に任意属性を追加するのみで、元のデフォルトトラフィックツールのバインドをレポート Agent まで拡張します。補完バインドツールはデフォルトでレポート Agent に委ねられます。カスタムバインドリスト、プロンプト、説明、および有効状態は保持されます。案内は最終的なツール組み立て後に一括で追加されます。報告ロールは既存証拠の引き継ぎを担い、レポート Agent は照合、バインド、レポート作成を担います。プラットフォームの対話でタスクコンテキストが欠落している場合は、構造化ヒントを通じてタスク Agent に引き継ぐべきで、直接報告しません。タスク完了を判定する前に、まず既存の証拠を引き継ぐべきです。バインドがなくても待機を強制しません。失敗した `report_finding` はレポート Agent をトリガーしません。

## API

ベースパス：`/api/exploration/findings/{finding_id}/traffic` で、独立した脆弱性 ID を使用します。認証を踏襲します。`context_task` はタスクの可視性と継承の読み取り専用を検証します。

| メソッド / 相対パス | リクエスト / 返り値 |
| --- | --- |
| `GET` | 順序付き概要、証拠バージョン、レポート採用バージョン |
| `POST` | `{"traffic_refs":[...]}` を一括追加 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"说明"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`、完全なリストでなければなりません |
| `GET /{binding_id}` | スナップショットのメタデータと境界付き本文プレビュー |
| `GET /{binding_id}/body` | `side`、`offset`、`length`。`download=1` で完全な生バイトをダウンロード |

バージョン/順序集合の競合、アーカイブ中の書き込みは `409` を返します。継承への書き込みは `403`、存在しないまたは脆弱性に属さないバインドは `404` を返します。トラフィック/添付の読み取りおよび検証の失敗は明確にエラーを返します。

## ストレージとマイグレーション

起動時に PostgreSQL へ冪等なマイグレーションを行います。`traffic_evidence_snapshots`、`finding_traffic_bindings`、および `findings.evidence_version` / `report_evidence_version`（デフォルト 0）を追加します。履歴のテキストに基づいて補完バインドを推測しません。

スナップショットは元のトラフィック ID、採取時刻、URL、メソッド、ステータス、リクエスト/レスポンスヘッダ、本文長、および SHA-256 を保存します。本文はハッシュに従い `<data>/evidence/blobs/<前两位>/<hash>.bin` に格納され、クリーンアップ可能な `data/traffic` とは独立しており、複数の脆弱性でスナップショット/本文を共有できます。スナップショットには内容更新のインターフェースを提供せず、検証が一致しない場合は読み取りとエクスポートが失敗します。

元のトラフィックの書き込みロック下で、大きな本文の blob や旧ディレクトリのレコードを含め、完全な本文を読み取ります。まずファイルを永続化して検証し、その後単一の PostgreSQL トランザクションで探索ノード、意図関係、脆弱性、スナップショット、バインドを書き込みます。コミット後にのみプランナーへ通知します。失敗すると参照のないファイルが残る可能性はありますが、部分的な業務レコードは生成されません。

PostgreSQL advisory lock `7337741004` が証拠ファイルと SQL 参照を調整します。タスク行ロックはアーカイブのキューイング後の証拠変更を禁止します。リカバリは本文のインストールからメタデータのコミットまで全工程で証拠ロックを保持します。脆弱性の削除はバインドをカスケードで除去します。

クリーナは毎時実行され、参照がなく進行中の操作でもないコンテンツのみを、少なくとも 24 時間遅延させて回収します。通常のトラフィッククリーンアップは証拠ディレクトリに触れません。ホットデータをバックアップする際は、PostgreSQL と `data/evidence` を同時にバックアップします。

## エクスポートとアーカイブ

Markdown には順序付きの証拠リストとバージョンが含まれ、JSON にはメタデータが含まれ、CSV には件数とバインド ID が追加されます。`md-zip` は脆弱性 Markdown を保持し、さらに次を提供します。

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown は相対リンクで通信内容を参照します。ダウンロードを送信する前に、添付のコピー、ハッシュ検証、圧縮、ディスク同期、および全 ZIP エントリの CRC 読み取り検証を完了します。欠落/破損があるとダウンロード全体が失敗します。完全な添付は生バイナリの原データを保持します。

アーカイブ v3 は脆弱性のバインド関係に従ってスナップショットと本文を収集し、元のトラフィックやドメインには依存しません。パッケージ検証の完了後にのみホットデータをクリーンアップします。共有証拠は引き続き保持されます。リカバリはまずインストールした本文を検証し、その後トランザクションでメタデータとバインドを復元し、失敗時の再試行をサポートします。v1/v2 は引き続き復元可能で、欠落した新フィールドは明示的に 0 で補います。

## 検証と境界

テストパッケージごとに独立した新規の PostgreSQL テスト DB を設定し、`ARTEX_PG_DSN` で指定して、残留したタスク/モデルのフィクスチャがバックグラウンド実行をトリガーするのを避けます。関連パッケージの完全なテストを実行し、設定の欠落によるスキップがないことを確認します。

```sh
# 每个包运行前将 ARTEX_PG_DSN 设为对应的独立测试库；显式配置失败必须报错。
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

フロントエンドの検証には `npx tsc --noEmit`、影響を受けるファイルの Biome チェック、Webpack ビルド、および `NEXT_EXPORT=1` の静的エクスポートが含まれます。独立したキャッシュディレクトリを使用し、実行中の開発サーバーを上書きしないようにします。

ローカルのエンドツーエンド受け入れでは、独立したポート、制御された HTTP / ドメイン HTTPS のターゲット、および一時データディレクトリを使用し、2 つのバインド入口、ページをまたいだ選択、並べ替え/説明、エラー表示、継承の読み取り専用、ダウンロード、さらに元のトラフィックを削除した後のエクスポート、アーカイブ、ホット本文の回収、復元とハッシュ検証をカバーします。

初版はグローバルな証拠協調ロックを採用します。大量のバインド/エクスポートや低速な添付ダウンロードの間、他の証拠操作が待機する可能性があります。録画記録や完全な本文が欠けている場合、証拠を捏造して補うことはできません。本機能はキャプチャのスイッチを変更せず、HTTPS で IP に直接アクセスする際の証明書問題も扱いません。
