# サイドバーの長い対話とコンテキスト予算

2026-09-11 の修正。元の実装はリクエスト JSON の文字数をそのまま token とみなし、さらにメインタスクの 32K 出力予約を継承していたため、HTML、JS、ツール結果が多い場合に正常なサイドバー質問を早々に拒否していました。

## オープンソース実装の照合

- [Grok CLI サイドバーコンテキスト](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/agent.ts#L739)：直近のユーザー・アシスタントのテキストから断片を抽出し、文字予算は約 2000、1 件あたり最大 400 文字まで切り出します。この経路では連続したサイドバー問答履歴を維持しません。
- [Grok CLI 独立リクエスト](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/utils/side-question.ts)：独立したキャンセルシグナル。モデルが対応している場合は出力上限 2048 tokens。ツールは提供しません。
- [Grok CLI メインセッション圧縮](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/compaction.ts)：token を見積もり、直近の内容を保持し、新しい内容を古い要約に更新し、ターンをまたぐ切り詰めを処理します。
- [OpenCode セッション圧縮](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/compaction.ts)：リクエスト全体の見積もり、出力／バッファの予約、直近の内容にローリング要約を加える方式、ツールなしの要約リクエスト。この実装のデフォルトは直近予算 8000、要約出力上限 4096 tokens です。
- [OpenCode オーバーフロー復旧](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/runner/llm.ts)：アシスタント出力がまだ始まっていない場合にのみオーバーフロー復旧を試み、復旧後の呼び出しは同じオーバーフロー復旧経路に再度入りません。

ARTEX は独立した出力予算、直近の内容とローリング要約、限定的な復旧というアプローチを取り入れています。norma v0.3.6 の構造化メッセージとツールペアリングを維持し、Grok のテキスト抜粋はそのまま流用しません。また OpenCode のメインセッション圧縮イベントを ARTEX のメイン transcript に書き込むこともしません。

## リクエスト予算と実行

- メッセージは norma のコンテンツブロック単位の UTF-8 バイト見積もりと 4/3 の余裕をそのまま使用し、さらにシステムプロンプト、ツール schema、メッセージのラッピングオーバーヘッドを加算します。見積もりはモデルの正確な token カウントではありません。
- サイドバー出力はデフォルトで最大 8192 tokens で、メイン設定にすでに設定された出力上限も超えません。サービス環境変数 `ARTEX_BTW_MAX_OUTPUT_TOKENS` で 256–32768 の上限を設定できます。製品のデフォルトモデルやメインタスクのパラメータは変更しません。
- 入力予算はコンテキストウィンドウから出力上限と安全余裕を引いたものです。ウィンドウが不明な場合はプラットフォームのデフォルト 200K を使用します。安全余裕はウィンドウの 5%、最小 128、最大 8192 tokens です。
- 成功した問答はインクリメントされる連番により 1 バッチあたり最大 20 組ロードします。最大 20 組の原文を保持し、その token 予算は入力予算の 1/4 を上限とし、かつ 16K を超えません。
- 超過した問答はローリング要約に更新します。要約には履歴の出典とコンテキスト時刻を付与します。履歴のアシスタント回答は新しいツール証拠と同等ではなく、矛盾する場合は最新のメインスナップショットを優先します。
- メインコンテキストがなお長すぎる場合は、複製中の古いメッセージのみを要約し、直近は最大 8K tokens を保持します。切り詰め点はツール呼び出しと結果を分割しません。大きすぎる単一の組は丸ごと要約に入ります。
- 要約の入力は実際の残りウィンドウに応じて UTF-8 安全にチャンク分割し、出力上限は 2048 tokens です。空の要約、切り詰め、ツール呼び出し、または要約予算の超過はいずれもキャッシュに書き込みません。1 回のサイドバーで要約呼び出しは最大 12 回とし、同一の 120 秒タイムアウト制限を受けます。上限に達すると明示的に失敗し、無限ループにはなりません。
- モデルが初回でコンテキスト超過を返し、かつまだテキストやツール呼び出しを出力していない場合は、さらに縮小した上で最大 1 回リトライします。見積もりサイズが減少しない場合は即座に復旧を停止します。その他のモデルエラーや部分的なストリーミング出力はこの復旧をトリガーしません。
- 取得済みの使用量はすべて、要約、失敗した試行、キャンセル時の使用量を含め、同一のサイドバーリクエストに累積します。Provider が使用量を返さない場合は依然としてゼロしか記録できず、見積もりを実際の使用量と偽ることはできません。

## 永続化とインターフェース

`side_question_sessions.memory` は、古い問答の要約、カバーされた ordinal、スナップショット ID ごとにキャッシュされたメインコンテキスト要約を保存します。`side_question_requests.context_info` は、準備段階、実際の再生組数、要約の使用状況、予算見積もりを保存します。

要約は元のリクエストがまだ実行中でクリーンアップバージョンが一致する場合にのみ保存します。クリアは同時にキャッシュを削除し、遅れて到着した書き込みはすでにクリアされたデータを復元しません。新しいスナップショットは古いスナップショットの要約を再利用しません。要約フィールドは v3 のタスクアーカイブとともに保存します。古い v3 で欠落フィールドを復元する際は空オブジェクトで補い、v1/v2 は引き続き互換性を保ちます。

POST はまずリクエストを受け入れて返し、準備と圧縮はバックグラウンドで実行され、受け入れロックやデータベーストランザクションを保持しません。SSE／履歴は、準備、問答の整理、複製の圧縮、回答の各段階を表示します。圧縮の失敗はそのサイドバーリクエストの失敗終了状態として保存します。フロントエンドはエラーを保持し、今回失敗した質問の下書きを復元します。フローティング通知で入力欄を覆うことはせず、履歴のポーリングが送信エラーを消去することもなくなりました。
